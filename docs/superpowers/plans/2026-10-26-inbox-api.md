# Inbox Conversation API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Store a real conversation for every Inbox thread (status, assignee, Later, unread, archive, reply window) and serve the redesigned Inbox's whole API — lists with correct keyset paging, detail, mutations with Undo, notes, saved replies, per-user settings, platform comment actions, scheduled replies with attachments, AI translate and quick replies, realtime, notifications — while every old write path keeps the new table right during the cutover window.

**Architecture:** `inbox_items` stays the message log and gains a generated `thread_key`. A new `inbox_conversations` row per `(workspace_id, thread_key)` is maintained by ONE write path, `ConversationSyncService.syncThread`, which re-aggregates the thread's items under a per-thread lock and applies a pure, table-tested lifecycle function. Every writer (ingest, old routes, new routes, Maestro, jobs) ends in that call (ruling R1). New code lives in `src/inbox/conversations/` inside the existing `InboxModule`; SQL-heavy services take `@Inject(DRIZZLE)` so they are proven against local Postgres in a rolled-back transaction.

**Tech Stack:** NestJS 11, Drizzle ORM 0.45 (PostgreSQL 17 locally), BullMQ 5.66, socket.io, ioredis, class-validator, Jest 30 + supertest.

## Global Constraints

- **Database safety:** never run `db:push`; never connect to, migrate or query the production database; never run `npm run inbox:backfill` (Task 10) against anything but localhost. Migrations are hand-written numbered `.sql` files in `drizzle/migrations/`, applied ONLY by the boot runner in deploys; locally they are exercised only through the rollback harness (the local `applied_migrations` table is empty, so `db:migrate:sql` would replay everything — do not run it). Read `docs/migrations.md`.
- **Migration rules:** idempotent (`IF NOT EXISTS`, `ADD VALUE IF NOT EXISTS`, constraints inside `DO $$ … EXCEPTION WHEN duplicate_object THEN NULL; END $$`), the repo header (`-- WHY`, `-- SAFETY`, `-- ROLLBACK`, "Never run `db:push` against prod. The boot migrator applies this file."), no `CONCURRENTLY`, no `BEGIN`/`COMMIT`. All new timestamp columns are `timestamptz`. Each migration ships its Drizzle schema change in `src/drizzle/schema/` (one file per new table, exported from `src/drizzle/schema/index.ts`).
- **NestJS:** Service-Controller-Module pattern; all new providers/controllers register in `src/inbox/inbox.module.ts` (no new module). Request bodies and queries are `class-validator` DTO classes; the global pipe is `ValidationPipe({ whitelist, forbidNonWhitelisted, transform })`, so every accepted key must be declared.
- **Route guards:** every new route sits under `inbox/workspaces/:workspaceId` (or `ai/workspaces/:workspaceId`), keeps `@UseGuards(JwtAuthGuard, WorkspaceRoleGuard)`, declares `@RequireCapability(...)` explicitly, and validates `:workspaceId` (and uuid ids) with `ParseUUIDPipe`. `inbox:view` = GUEST, `inbox:reply` = MEMBER (`src/workspace-members/role-capabilities.ts`). `src/workspace-members/every-workspace-route-guarded.spec.ts` must stay green; never add to its allowlist. Every controller task has an HTTP spec that asserts each handler's capability metadata and that a GUEST gets 403 on every `inbox:reply` route.
- **Contract fidelity:** response and payload types are copied verbatim into `src/inbox/conversations/dto/contract.ts` (Task 6) and imported from there; names and fields match the contract exactly. Error bodies named by the contract: `409 { code: 'REPLIED_FIRST', reply }`, send failures `{ code, message, retryable }`, comment actions `400 { reason }`, saved-reply shortcut clash `409`.
- **Cutover compatibility (R1):** the old Inbox, the Planner post dialog and Home keep calling the old routes until the frontend switch. Until Task 25 (post-cutover branch):
  - no old route is removed and no old request field is dropped;
  - an existing route whose response changes returns the UNION of its old body and the new keys (`{ ...legacy, node, row }` and so on) — listed in Tasks 18 and 20;
  - `inbox.item.*`, `scheduled.message.*` and `inbox.counts.changed` events keep firing with their OLD payloads; the new counts go out as a separate event, `inbox.conversation.counts.changed { workspaceId, counts }` (Task 7);
  - legacy bodies stay accepted: `POST scheduled` with `type`+`threadKey`+`scheduledAt`, `PATCH scheduled/:id` with `scheduledAt`, `POST ai/.../suggest-reply` with `platform`+`messages`. (`ScheduledDto` is a permanent superset per the contract — the Planner keeps the old fields.)
- **Time:** conversation timestamps are written truncated to milliseconds (`date_trunc('milliseconds', …)`) so a cursor round-trips through JS exactly. Day boundaries and Later presets use the WORKSPACE time zone (`loadWorkspaceTimezone`, `wallClockToUtc`, `localDateOf`, `zonedClock` from `src/planner/lib/workspace-time.ts`; an invalid zone is UTC). Anything compared to "now" takes an injected `now: Date` or uses jest fake timers; no hard-coded future dates.
- **BullMQ:** job ids never contain `:`.
- **Style and git:** Prettier single quotes, trailing commas. Never skip hooks, never push or merge, never `git stash` (compare with `git show origin/main:<path>`). Every commit message ends with `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.

## Review Focus

1. **A busy post with hundreds of comments.** One post thread with 400 comments must page as ONE row, count `unreadCount: 400`, sync each new comment in bounded work (one aggregate over the thread, not N queries), and not flood sockets during a first backfill. Tests: Task 7 (400-comment sync; 400 change notifications inside 300 ms emit one upserted event), Task 11 (a chatty thread never shortens a page), Task 12 (detail for 300 comments loads users in one query).
2. **The cutover window (R1).** Between backend deploy and frontend switch, old routes, ingest and Maestro still write rows; the conversation must follow, and the re-run backfill must not wipe status, assignee or Later set meanwhile. Tests: Task 9 (every old write route ends in `syncThread` with the right intent), Task 10 (backfill then `syncThread` is a no-op; re-running the backfill keeps `status`, `assignee_user_id`, `later_until`).
3. **Two teammates sending at once.** The second send must wait for the first and then get `409 REPLIED_FIRST` carrying the first reply, unless `force: true`. On a busy post, replies to DIFFERENT comments must not collide. Tests: Task 18.
4. **A Later wake racing an inbound message.** A wake job that fires after an inbound already moved the conversation to `to_reply` (or after the user re-snoozed to a new time) must change nothing. Tests: Task 4 (pure wake rule), Task 14 (DB race and stale job).
5. **YouTube redaction.** The 30-day retention job wipes item text and author; the conversation's denormalised `last_snippet`, `last_author_label`, `participant_*` and `search_text` must be wiped too, rows must report `contentRedacted: true`, and search must no longer match the wiped words. Tests: Task 8.

### Task 1: Rollback harness that survives nested transactions, plus inbox fixtures

**Why first:** `withRollbackDb` (`src/planner/testing/rollback-db.ts`) hands services a drizzle instance built on one `pg.Client` after a raw `BEGIN`. Drizzle's `db.transaction()` on a non-Pool client issues its own `begin` … `commit` (`node_modules/drizzle-orm/node-postgres/session.js:181-196`), which COMMITS the harness transaction: the migrations and fixtures persist in the local DB and the final `ROLLBACK` is a no-op. `syncThread` runs in a transaction, so every DB spec in this plan would leak. Nested `tx.transaction()` uses savepoints, so the fix is to hand `fn` a transaction object.

**Files:**
- Modify: `src/planner/testing/rollback-db.ts`
- Create: `src/planner/testing/rollback-db.db.spec.ts`, `src/inbox/testing/inbox-db.ts`, `src/inbox/testing/inbox-db.db.spec.ts`

**Interfaces:**
- Produces (`rollback-db.ts`, same exports and signature): `withRollbackDb<T>(migrations: string[], fn: (db: DbType, client: PoolClient) => Promise<T>): Promise<T>` now runs `drizzle(client, { schema }).transaction(async (tx) => { SET LOCAL TIME ZONE 'Asia/Karachi'; apply each file twice via client.query; result = await fn(tx as unknown as DbType, client); throw new RollbackSignal(result) })`, catches `RollbackSignal` and returns its value; any other error is rethrown (the transaction is rolled back either way). `describeDb` and `assertLocalDatabase` unchanged.
- Produces (`inbox-db.ts`):
  - `INBOX_MIGRATIONS: string[]` — starts `[]`; Tasks 2, 3, 10 and 13 append their files in order.
  - `describeInboxDb = describeDb`; `withInboxDb<T>(fn: (db: DbType, client: PoolClient) => Promise<T>, extra: string[] = []): Promise<T>` = `withRollbackDb([...INBOX_MIGRATIONS, ...extra], fn)`.
